# Spring Boot Practices

Use these practices for Spring Boot applications from version 2.2 through 4.1.

## Build and Packaging Compatibility

- Spring Boot supports Maven and Gradle. Use `spring-boot-maven-plugin` for Maven or `org.springframework.boot` for Gradle; keep the plugin requirement conditional on the selected build tool.
- Executable JAR packaging uses an embedded servlet container and does not support JSP. Choose a compatible view technology before selecting executable JAR packaging.
- Spring Boot WAR packaging is a valid alternative when JSP or external servlet-container deployment must remain. WAR and Thymeleaf are not inherently incompatible.
- Do not declare framework, build-tool, packaging, and view choices incompatible based only on their categories. Confirm the specific combination against official Spring Boot documentation and project behavior.

## 1. Prefer Constructor Injection

Prefer constructor injection and final dependencies.

```java
@Service
public class OrderService {

    private final OrderRepository orderRepository;

    public OrderService(OrderRepository orderRepository) {
        this.orderRepository = orderRepository;
    }
}
```

Avoid field injection with `@Autowired`.

## 2. Keep Controllers Thin

Controllers should handle HTTP concerns only.

```text
Controller
    -> Service
    -> Repository / External Systems
```

Keep business logic in services or domain classes.

## 3. Do Not Expose JPA Entities Directly

Use dedicated request and response DTOs.

```java
public record UserResponse(
        Long id,
        String name,
        String email) {
}
```

For older Java versions used with Spring Boot 2.x, use normal immutable DTO classes instead of records.

## 4. Validate Input at Boundaries

Use Bean Validation for incoming API requests and configuration.

Spring Boot 2.x commonly uses:

```java
javax.validation.Valid
```

Spring Boot 3+ uses:

```java
jakarta.validation.Valid
```

## 5. Use Centralized Exception Handling

Prefer centralized exception mapping:

```java
@RestControllerAdvice
public class GlobalExceptionHandler {
}
```

Avoid repetitive `try/catch` logic in every controller. For modern Spring versions, prefer standardized error responses such as `ProblemDetail`.

## 6. Use Transactions Intentionally

Place transaction boundaries around meaningful business operations.

```java
@Transactional
public void createOrder() {
    ...
}
```

For reads:

```java
@Transactional(readOnly = true)
public Order getOrder(Long id) {
    ...
}
```

Avoid unnecessarily long transactions and external network calls inside database transactions.

## 7. Avoid N+1 Queries

Do not solve persistence problems by making every relationship `EAGER`.

Use appropriate fetch joins, entity graphs, DTO projections, batch fetching, or explicit queries. Always understand important SQL generated by Hibernate.

## 8. Use Spring Boot Dependency Management

Prefer versions managed by Spring Boot. Avoid manually overriding Spring Framework, Spring Security, Hibernate, Jackson, and related dependency versions unless necessary. Do not mix incompatible framework generations.

## 9. Use Typed Configuration

Prefer typed configuration:

```java
@ConfigurationProperties(prefix = "payment")
public class PaymentProperties {
    ...
}
```

Use records when supported by the target Java and Spring Boot generation. Avoid spreading large numbers of `@Value` annotations throughout the application.

## 10. Keep Secrets Outside the Application

Never hardcode passwords, tokens, API keys, private keys, or credentials. Use environment variables, platform secrets, Vault, cloud secret managers, or another approved secret-management system.

## 11. Configure Security Explicitly

Modern Spring Security applications should prefer `SecurityFilterChain`.

```java
@Bean
SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
    return http
            .authorizeHttpRequests(auth -> auth
                    .anyRequest().authenticated())
            .build();
}
```

Never rely only on frontend authorization.

## 12. Preserve Server-Side Authorization

Use URL-level and method-level authorization where appropriate.

```java
@PreAuthorize("hasRole('ADMIN')")
public void deleteUser(Long id) {
    ...
}
```

Never weaken authorization simply to fix framework or test failures.

## 13. Use Structured Logging

Prefer structured logging.

```java
log.info("Order created orderId={} customerId={}",
        orderId,
        customerId);
```

Avoid `System.out.println`. Never log passwords, tokens, authorization headers, or other sensitive information.

## 14. Add Production Observability

Use Spring Boot Actuator for health, metrics, readiness, liveness, and application information. Use Micrometer for metrics and modern Spring versions' observation/tracing support when required.

Do not expose sensitive Actuator endpoints publicly.

## 15. Configure Timeouts for External Calls

Every external HTTP, database, or network dependency should have appropriate connection, read, request, and pool timeouts. Do not allow remote calls to wait indefinitely.

## 16. Use Retries Carefully

Retry only transient and safely retryable operations. Account for idempotency, maximum attempts, backoff, and duplicate side effects. Never implement infinite retries.

## 17. Choose MVC or WebFlux Intentionally

Use Spring MVC for conventional synchronous applications. Use WebFlux when there is a real requirement for reactive, non-blocking I/O. Do not choose WebFlux simply because it is newer.

## 18. Use Async Execution Carefully

When using `@Async`, understand executor configuration, thread limits, queue limits, exception handling, transactions, and context propagation. Avoid unbounded executors.

## 19. Test at the Correct Level

Prefer plain unit tests for business logic.

```text
@WebMvcTest      web/controller tests
@DataJpaTest     persistence tests
@SpringBootTest  full integration tests
```

Do not start the complete Spring context for every test.

## 20. Prefer Real Infrastructure for Integration Tests

Use Testcontainers where appropriate for PostgreSQL, MySQL, Kafka, Redis, MongoDB, RabbitMQ, and similar dependencies. Do not mock infrastructure when the purpose of the test is to verify real integration behavior.

## 21. Organize by Feature Where Practical

Prefer feature-oriented package boundaries when they fit the codebase.

```text
order/
    OrderController
    OrderService
    OrderRepository
    Order
    OrderResponse

payment/
    PaymentController
    PaymentService
    PaymentRepository
```

Avoid very large global `controller/`, `service/`, and `repository/` packages when feature packages would be clearer.

## 22. Use Framework APIs, Not Spring Internals

Avoid depending on undocumented Spring implementation classes. Prefer official extension points such as `@Bean`, `@Configuration`, `Converter`, `WebMvcConfigurer`, `SecurityFilterChain`, `HandlerMethodArgumentResolver`, and `ApplicationListener`.

This reduces upgrade difficulty.

## 23. Handle `javax` and `jakarta` According to Version

Spring Boot 2.x commonly uses Java EE `javax.*`.

Spring Boot 3+ uses Jakarta EE `jakarta.*`.

```text
Boot 2.x:
javax.persistence.Entity

Boot 3/4:
jakarta.persistence.Entity
```

Do not blindly replace all `javax.*`; packages such as `javax.sql`, `javax.crypto`, and `javax.xml` remain JDK APIs.

## 24. Use Modern APIs Only When They Add Value

Newer Spring Boot and Java versions provide capabilities such as records, virtual threads, HTTP Interfaces, `ProblemDetail`, AOT/native images, improved observability, API versioning, and gRPC.

Use them when they simplify the application or solve a real problem. Do not modernize code merely because a newer API exists.

## 25. Keep Code Compatible With the Spring Boot Generation

Think in generations:

```text
Spring Boot 2.x
-> Spring Framework 5
-> javax ecosystem

Spring Boot 3.x
-> Spring Framework 6
-> Jakarta ecosystem

Spring Boot 4.x
-> Spring Framework 7
-> Jakarta EE 11 / newer dependency baseline
```

When upgrading, review framework, security, persistence, serialization, and configuration behavior together.

## Core Principle

Prefer Spring Boot code that is simple, explicit, testable, secure, observable, and maintainable. Use the simplest Spring Boot approach that preserves clear application behavior across the supported framework generation.
